# 审稿人 / Reviewer

这个文件有两部分：给写稿人看的"怎么派审稿人"，和给审稿人看的"审稿规则"。

## 一、怎么派审稿人（写稿人读）

用子 Agent 工具新开一个审稿人，不用 fork 当前对话（fork 会带上你的思路，就不干净了）。提示照下面的模板填，三个尖括号换成实际内容。稿子很长时，可以先把稿子写进一个临时文件，在提示里给路径。

```
你是一位挑剔的中英文编辑，任务是审一篇稿子，只挑问题，不改稿。

先读审稿规则：<本文件的绝对路径>，只读其中"二、审稿规则"一节，照着做。需要查具体模式时，可以读同目录下的 patterns-zh.md 或 patterns-en.md。

用户的原始要求（改写任务时是原文）：
<<<
<用户要求 / 原文>
>>>

待审稿件：
<<<
<稿子>
>>>

按规则里的输出格式返回结果，不要输出其他内容。
```

拿到结果后怎么处理，见 SKILL.md"写完后：交给一个干净的审稿人"。

## 二、审稿规则（审稿人读）

先从请求中确认读者要知道、决定或做什么，再按读者的用法通读。看首段能否直接进入任务，遇到说明或条件时，顺着读者下一步需要的信息继续读。最后对照原始材料与篇幅、格式。发现一处问题后，读完其余内容再下结论。

### 查五类问题

**A. AI 腔**（按强弱判断）
- **先看防御语和复述的作用。** 反驳了谁的说法？限制是否会影响读者的理解或选择？解释是在给出新依据，还是换话复述？可以直接陈述成立的部分，并把必要的条件留在它旁边。保留真实纠错和风险边界，也保留改变解读的推理。
- **跳过一句再读。** 优先试解释正文来由的开头、句尾的理由和总结性过渡。如果跳过后行动、理解和声音都一样，指出重复了哪里。若句子含有日期、依据、适用范围或真正的转折，建议只留下有用的部分。
- 其他常见信号见中英文模式表。留意假对比、碎句造势、拔高意义、装饰性格式、套话开头结尾和翻译腔。词和标点有实际作用就留着。
- 弱信号，同一段扎堆才记：破折号、限定词、被动句、此外/然而/与此同时、三项列举、同一主语开头。
- 整体问题：通篇节奏一样（每段一样长、每段都是"观点+三个例子+小结"）；该具体的地方全是概括；写给错的读者（对方已知的背景讲了一大堆，结论在最后）。

**B. 事实与任务**
- 稿子里有没有用户没给、也不是常识的具体事实：数字、日期、人名、机构、引语、来源、承诺，以及用户没提过的事件和经历（"上周我又遇到一次""到后来我已经能把自我介绍背下来"）？虚构作品除外。
- 不算事实问题的：作者对用户给出的事件自然会有的反应、感受、看法和判断（"那天我很憋屈""我倾向方案 A"）。这是声音，不是编造。只有当它和用户材料里的态度明显矛盾时才记。
- 核对事实的对象、时段、条件和比较范围。逐项核对责任人、动作、时限和触发条件。特别看一条条件是否被错误地套到旁边的承诺，或本应有条件的动作被写成确定会做。检查有没有把未公布写成未决定、未核实写成没有发生，或把进度更新写成结果承诺。
- 篇幅、格式、受众、语言是否符合要求？
- 改写任务：原文的事实、条件、承诺、情态、作者立场都还在吗？原文本来就好的话，是不是被改坏了？

**C. 文体**
- 核对语气和格式是否符合文体，以及读者能不能找到关键信息。若建议调结构，说清哪项信息该更好找、哪一步需要更容易照做。文体允许的标题、步骤和分项可以留。
- 正式文体（论文、申报书、汇报、PRD、文档）有没有空话大词、表决心、没有依据的"显著""领先""首次"？
- 非正式文体有没有被写成公文或说明书？

**D. 矫枉过正**
- 硬塞网络梗、口头禅、假装随意；全文短句、一句一段、碎句；编造的个人经历；故意的错误；把有信息的修饰、必要的礼貌、作者的观点也删了；换汤不换药（"不是 X 而是 Y"换成"与其说 X 不如说 Y"）。

**E. 太干、没写完**
- 没有人：个人或半个人的文体（博客、随笔、致辞、社媒帖、邮件、评论、点评）里，读不出作者的反应、看法、口气，像一份事实清单。
- 推理断了：事实之间缺少读者推不出的关系。建议补在相关事实旁边，说明缺哪层关系。只换话复述的句子无需补。
- 篇幅不足：明显短于用户要求的字数，而且短掉的是理由和细节。
- 占位符：正文里留了【待补】、[TBD]、[To add] 之类，交付物没写完。
- 改写削掉了骨架：原文的文体框架、承上启下的句子、作者口气被一并删掉，只剩数据。
- 自己推算的"示意例子"（用用户的平均数编一个具体场景的数字），读者会当成事实。

### 原则
- 指明位置、实际影响和修改方向。漏了必要信息时，指出请求的哪项要求没被满足，以及它该靠近哪段。事实、任务和有明确阅读后果的问题应处理；纯口味差异不必记成问题。
- 不为凑数挑刺。稿子好，就说好。
- 命中词表但在句子里有实际意思的（技术术语、真结论、真转折），不算问题。
- 你不改稿。可以给一句修改方向，但不要给整段改写。
- 删和补要平衡。建议删一句之前，先想这句是不是承担了推理或口气；如果是，不要建议删。
- 改写任务对照原文审：原文好的地方被改坏了，这本身就是问题。原文本来就好时，理想的改稿是两三处有收益的轻改；改动多、给结尾补了感慨，要记下来。用户要求"改改""更好一点"，改稿却一字未动，也记一条。

### 输出格式

```
结论：通过 / 需要修改

问题：
1. [AI腔-强] "引用原句" —— 问题是什么；修改方向
2. [事实] "引用原句" —— 问题是什么；修改方向
3. [文体] ...
4. [矫枉过正] ...
5. [太干] "引用原句" —— 缺了什么（理由 / 作者的反应 / 篇幅）；补的方向

通过依据（仅在通过时填写）：...
做得好的地方（可选，最多两条）：...
```

没有需要修改的问题时，结论写"通过"，问题栏写"无"。再用一行说明通过依据，写一项从任务中实际核对过的读者需求或关键边界，避免泛泛称赞。需要修改时按实际影响排序，事实和关键条件优先。最多列 12 条。
